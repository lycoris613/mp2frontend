## 1. API 설계 개요

### 1.1 설계 목적

> React 프론트엔드와 Spring Boot 백엔드, 그리고 Spring Boot와 FastAPI LLM 서비스 간의
통신 규격을 정의하여, **비동기 분석 파이프라인**을 일관되게 구현할 수 있도록 한다.
> 

### 1.2 설계 원칙

- **RESTful 아키텍처**: HTTP 메서드와 상태 코드의 올바른 사용
- **2단계 파이프라인의 가시화**: 탐지(Scanner)와 설명(LLM)은 소요 시간이 크게 다르므로 상태를 분리해 노출한다
- **비동기 우선**: 분석 요청은 즉시 `202 Accepted`를 반환하고 폴링으로 진행 상황을 전달한다
- **소유권 기반 인가**: 모든 분석 리소스는 생성한 사용자만 접근할 수 있다
- **일관성**: 모든 응답을 공통 래퍼(`success` / `data` / `message` / `timestamp`)로 감싼다
- **버전 관리**: URL 경로로 버전 구분 (`/api/v1`)
- **내부 API 분리**: LLM 서비스는 프론트에 노출하지 않고 백엔드만 호출한다 (BR-L006)

### 1.3 기술 스택

- **프레임워크**: Spring Boot 4.0.8 (Java 17)
- **인증**: JWT (AccessToken)
- **직렬화**: JSON (Jackson)
- **LLM 서비스**: FastAPI (Python) — OpenAPI 3.1 자동 문서화
- **API 문서**: springdoc-openapi (Swagger UI)
- **CORS 허용 오리진**: `http://localhost:5173`, `http://localhost:3000`

## 2. API 공통 규칙

### 2.1 URL 설계 규칙

| 규칙 | 설명 | 좋은 예 | 나쁜 예 |
| --- | --- | --- | --- |
| **명사 사용** | 동사가 아닌 명사로 리소스 표현 | `/api/v1/analyses` | `/api/v1/getAnalysis` |
| **복수형 사용** | 컬렉션은 복수형 | `/api/v1/findings` | `/api/v1/finding` |
| **계층 구조** | 리소스 관계를 URL로 표현 | `/api/v1/analyses/12/findings` | `/api/v1/getAnalysisFindings` |
| **소문자·하이픈** | URL은 소문자, 단어 구분은 하이픈 | `/api/v1/dashboard/summary` | `/api/v1/dashboardSummary` |
| **상태 변경은 서브리소스** | 부분 상태 변경은 PATCH + 하위 경로 | `PATCH /findings/5/status` | `POST /updateFindingStatus` |

> **명명 주의**: `analysis`의 복수형은 `analyses`이다. 프론트·백엔드 모두 이 철자를 사용한다.
> 

### 2.2 HTTP 메서드 사용 규칙

| 메서드 | 용도 | 멱등성 | 안전성 | 예시 |
| --- | --- | --- | --- | --- |
| **GET** | 리소스 조회 | ✅ | ✅ | `GET /api/v1/analyses` |
| **POST** | 리소스 생성 / 작업 트리거 | ❌ | ❌ | `POST /api/v1/analyses` |
| **PATCH** | 부분 수정 | ❌ | ❌ | `PATCH /api/v1/findings/5/status` |
| **DELETE** | 리소스 삭제 | ✅ | ❌ | `DELETE /api/v1/analyses/12` |

> PUT은 본 API에서 사용하지 않는다. 분석 결과는 생성 후 전체 교체 대상이 아니기 때문이다.
> 

### 2.3 HTTP 상태 코드 가이드

| 코드 | 상태 | 본 프로젝트 사용 예시 |
| --- | --- | --- |
| **200** | OK | 조회 성공, 상태 변경 성공 |
| **201** | Created | 회원가입 성공 |
| **202** | Accepted | **분석 요청 접수** (탐지 → 설명 비동기 처리 시작) |
| **204** | No Content | 로그아웃, 분석 삭제 성공 |
| **400** | Bad Request | 입력값 검증 실패, 지원하지 않는 언어 |
| **401** | Unauthorized | 토큰 없음/만료, 로그인 실패 |
| **403** | Forbidden | 타인의 분석 접근 시도 |
| **404** | Not Found | 존재하지 않는 분석/취약점 ID |
| **409** | Conflict | 이메일 중복, 이미 해결된 취약점 재해결 |
| **413** | Payload Too Large | 파일 크기/총 코드 크기 초과 |
| **422** | Unprocessable Entity | 상태 전이 위반 (진행 중 분석 삭제 등) |
| **502** | Bad Gateway | LLM 서비스 호출 실패 |
| **500** | Internal Server Error | 예기치 못한 오류 |

### 2.4 공통 요청 헤더

```
Content-Type: application/json
Accept: application/json
Authorization: Bearer {ACCESS_TOKEN}
```

## 3. 인증 및 권한 관리

### 3.1 JWT 토큰 기반 인증

#### 3.1.1 회원가입

```yaml
POST /api/v1/auth/signup
Content-Type: application/json
Public API (인증 불필요)

Request Body:
{
  "email": "dev@codeguard.dev",
  "password": "codeguard123!"
}

Validation Rules:
- email: 필수, 이메일 형식, 중복 불가 (BR-U001)
- password: 필수, 8-64자, 영문+숫자 조합 포함 (BR-U003)

Response (201 Created):
{
  "success": true,
  "data": {
    "id": 1,
    "email": "dev@codeguard.dev",
    "createdAt": "2026-09-27T14:30:00"
  },
  "message": "회원가입이 완료되었습니다"
}

Response (409 Conflict):
{
  "success": false,
  "statusCode": 409,
  "errorCode": "EMAIL_DUPLICATE",
  "message": "이미 사용 중인 이메일입니다"
}
```

#### 3.1.2 로그인

```yaml

Content-Type: application/json
Public API

Request Body:
{
  "email": "dev@codeguard.dev",

Response (200 OK):
```

### 3.2 권한 레벨 정의

| 역할 | 권한 | 설명 |
| --- | --- | --- |
| **ANONYMOUS** | 회원가입, 로그인 | 그 외 모든 API 차단 |
| **USER** | 본인 분석의 생성·조회·삭제, 취약점 상태 변경 | MVP의 유일한 인증 역할 |

> 별도 ADMIN 역할은 MVP 범위에서 제외한다 (BR-U004에 따라 소유권 검사만 수행).
> 

### 3.3 소유권 검사 규칙

모든 `/analyses/**`, `/findings/**` 요청은 다음 순서로 검사한다.

```
1. 토큰 유효성 → 실패 시 401
2. 리소스 존재 여부 → 없으면 404
3. 리소스 소유자 == 토큰 사용자 → 불일치 시 403
```

### 4.1 분석 요청 API

#### 4.1.1 분석 요청 생성 및 시작 ⭐

```yaml
POST /api/v1/analyses
Content-Type: application/json
Authorization: Bearer {ACCESS_TOKEN}

Request Body:
{
  "title": "payments-api",
  "scanOptions": {
    "detectSqlInjection": true,
    "detectHardcodedSecret": true,
    "detectXss": true
  },
  "files": [
    {
      "relativePath": "src/routes/users.ts",
      "content": "import express from 'express';\nimport db from './database';\n\napp.get('/api/users', async (req, res) => {\n  const userId = req.query.id;\n  const query = `SELECT * FROM users WHERE id = ${userId}`;\n  const result = await db.query(query);\n  res.json(result.rows);\n});"
    },
    {
      "relativePath": "src/routes/payments.ts",
      "content": "..."
    }
  ]
}

Validation Rules:
- title: 필수, 1-100자
- files: 필수, 1-20개 (BR-A002)
- files[].relativePath: 필수, 500자 이내, 배열 내 중복 불가 (BR-A009)
- files[].content: 필수, 비어 있지 않음, 100KB 이하 (BR-A003)
- 전체 content 합계: 500KB 이하 (BR-A003)
- scanOptions: 선택, 미지정 시 3종 모두 true (화면의 `비밀 키 탐지 사용/미사용` 설정에 대응)

Response (202 Accepted):
{
  "success": true,
  "data": {
    "analysisId": 128,
    "title": "payments-api",
    "status": "PENDING",
    "totalFiles": 2,
    "estimatedDurationSeconds": 45,
    "createdAt": "2026-09-27T14:32:18"
  },
  "message": "분석 요청이 접수되었습니다"
}

Response (413 Payload Too Large):
{
  "success": false,
  "statusCode": 413,
  "errorCode": "CODE_SIZE_EXCEEDED",
  "message": "전체 코드 크기가 500KB를 초과했습니다"
}

Response (400 Bad Request):
{
  "success": false,
  "statusCode": 400,
  "errorCode": "UNSUPPORTED_LANGUAGE",
  "message": "지원하지 않는 파일 형식입니다: .png"
}
```

**처리 흐름**

```
① 요청 검증 → ② AnalysisRequest(PENDING) + AnalysisFile N건 저장 (트랜잭션 커밋)
→ ③ 202 즉시 응답 → ④ @Async 워커: Scanner 탐지 → LLM 설명 (§4.6 참조)
```

> `estimatedDurationSeconds`는 **추정값**이며 DB에 저장하지 않는다.
산식: `5초(탐지) + 예상 취약점 수 × 6초` — 탐지 전에는 취약점 수를 모르므로 `파일 수 × 20초`로 근사한다. 
(코드 분석 화면의 `예상 분석 시간 약 45초` 표시에 사용)
> 

#### 4.1.2 분석 진행 상태 조회 (폴링) ⭐

```yaml
GET /api/v1/analyses/{analysisId}/status
Authorization: Bearer {ACCESS_TOKEN}

Path Parameters:
- analysisId: integer (required)

Response (200 OK) — 탐지 단계:
{
  "success": true,
  "data": {
    "analysisId": 128,
    "status": "SCANNING",
    "stage": "SCAN",
    "stageLabel": "규칙 기반 탐지 중",
    "progress": 28,
    "currentFile": "src/routes/users.ts",
    "processedFiles": 1,
    "totalFiles": 2,
    "findingsSoFar": 3,
    "startedAt": "2026-09-27T14:32:19"
  }
}

Response (200 OK) — 설명 생성 단계:
{
  "success": true,
  "data": {
    "analysisId": 128,
    "status": "EXPLAINING",
    "stage": "EXPLAIN",
    "stageLabel": "AI 설명 생성 중",
    "progress": 71,
    "totalFindings": 23,
    "explainedFindings": 12,
    "recentLogs": [
      { "time": "14:32:21", "message": "동적 SQL 쿼리 발견 (SQLI-003)" },
      { "time": "14:32:22", "message": "CWE-89 규칙과 대조" },
      { "time": "14:32:27", "message": "AI 설명 생성 중 (12/23)" }
    ]
  }
}

Response (200 OK) — 완료:
{
  "success": true,
  "data": {
    "analysisId": 128,
    "status": "COMPLETED",
    "stage": "DONE",
    "progress": 100,
    "totalFiles": 2,
    "totalFindings": 23,
    "overallSeverity": "CRITICAL",
    "durationSeconds": 47,
    "completedAt": "2026-09-27T14:33:06"
  }
}

Response (200 OK) — 실패:
{
  "success": true,
  "data": {
    "analysisId": 128,
    "status": "FAILED",
    "stage": "SCAN",
    "errorMessage": "코드를 분석하는 중 오류가 발생했습니다. 다시 시도해 주세요."
  }
}
```

**진행률(progress) 산출 방식**

| 단계 | 구간 | 산식 |
| --- | --- | --- |
| `SCANNING` | 0 ~ 40% | `처리 완료 파일 수 / 전체 파일 수 × 40` |
| `EXPLAINING` | 40 ~ 100% | `40 + 설명 완료 건수 / 전체 취약점 수 × 60` |
| 탐지 0건 | — | 탐지 종료 즉시 100% |

**폴링 규칙**

- 프론트엔드는 **2초 간격**으로 호출하고, `status`가 `COMPLETED` 또는 `FAILED`가 되면 중단한다.
- 최대 폴링 시간은 **220초**(탐지 30초 + 설명 180초 + 여유)이며 초과 시 타임아웃 안내를 표시한다.
- `recentLogs`는 최근 5건만 내려주는 **휘발성 값**이며 DB에 저장하지 않는다 (D-12).
탐지 단계가 룰 기반이라 "어느 룰이 무엇을 발견했는지"를 즉시 알 수 있어, 화면 하단 로그를 실제 데이터로 채울 수 있다.

> **외부에 노출하지 않는 내부 전용 API**이다. Spring Boot만 호출한다 (BR-L011).
**v1.1 변경**: 탐지는 Spring Boot 내부 Scanner가 수행하므로, LLM 서비스는 **이미 탐지된 취약점 1건을 설명**하는 역할만 한다.

**요청 설계 포인트**

| 항목 | 방침 | 이유 |
| --- | --- | --- |
| 호출 단위 | 취약점 **1건당 1회** | 프롬프트가 단순해져 응답 품질·파싱 안정성이 높다 |
| 코드 범위 | 취약 라인 기준 **±20줄** | 파일 전체를 보내지 않아 토큰을 크게 절감한다 |
| 라인 번호 | `"6: const query = ..."` 형식으로 **번호를 붙여 전달** | LLM이 어느 줄을 설명하는지 혼동하지 않는다 |
| 룰 정보 전달 | `rule.description`을 함께 전달 | 무엇이 왜 걸렸는지 LLM이 이미 알고 시작하므로 설명이 정확해진다 |
| 심각도 | 요청에 포함하되 **응답에서 받지 않음** | 심각도는 룰이 결정한다 (BR-L002) |

**응답 스키마 계약**

| 필드 | 타입 | 필수 | 허용값 / 제약 | 누락·오류 시 처리 |
| --- | --- | --- | --- | --- |
| `verdict` | string | ✖ | TRUE_POSITIVE / FALSE_POSITIVE / UNCERTAIN | `UNCERTAIN` 저장 |
| `confidence` | integer | ✖ | 0~100 | null 저장 |
| `explanation` | string | ✔ | 1자 이상 | 누락 시 스키마 검증 실패 → 재시도 |
| `riskDescription` | string | ✖ | — | null 저장 |
| `attackScenario` | string | ✖ | — | null 저장 |
| `remediation` | string | ✔ | 1자 이상 | 누락 시 스키마 검증 실패 → 재시도 |
| `fixedCode` | string | ✖ | — | null이면 AFTER 영역 미표시 |
| **(금지)** `severity`, `startLine`, `vulnerabilityType` | — | — | — | **응답에 있어도 무시한다.** LLM은 탐지 결과를 바꿀 수 없다 (BR-L002) |

**프롬프트 설계 방침 (요약)**

1. 시스템 프롬프트에서 역할을 "보안 코드 리뷰어"로 고정하고 **JSON만 출력**하도록 지시한다.
2. **"이미 탐지된 취약점을 설명하는 역할"임을 명시**한다. 새 취약점을 찾거나 심각도를 바꾸지 말라고 못박는다.
3. 룰의 `title`·`description`을 함께 주어 설명의 방향을 고정한다.
4. 설명은 "보안 비전공 개발자가 읽는다"는 조건을 포함한다.
5. `fixedCode`는 **해당 구간만** 교체 가능한 형태로 출력하도록 요구한다 (파일 전체 재작성 금지).
6. 탐지가 오탐으로 보이면 설명을 지어내지 말고 `verdict: FALSE_POSITIVE`와 그 이유를 `explanation`에 쓰도록 지시한다.
7. 프롬프트 변경 시 `promptVersion`을 올리고 DB에 함께 기록한다 (BR-L009).

#### 4.5.2 헬스체크

> Spring Boot 기동 시 1회 호출해 LLM 서비스 가용 여부를 로그로 남긴다.
**LLM 서비스가 내려가 있어도 탐지 단계는 정상 동작한다.** 이 경우 취약점은 저장되고 설명만 비어 있게 된다.

### 4.6 비동기 분석 처리 흐름 (내부 동작)

```
[React]  POST /api/v1/analyses
              │
              ▼
[Spring] AnalysisService.createAndStart()
         ├─ 검증 + AnalysisRequest(PENDING) + AnalysisFile N건 저장  (트랜잭션 커밋)
         └─ 202 Accepted 반환 { analysisId }
              │
              ▼  (@Async, 별도 스레드)
[Spring] AnalysisWorker.run(analysisId)
         │
         ├─ ① request.startScanning()                      → 상태 SCANNING
         │   for each AnalysisFile:
         │      RuleCatalog.forLanguage(file.language)
         │        → 라인 단위 정규식 매칭
         │        → 오탐 제외 조건 적용 (주석/환경변수/바인딩)
         │        → 중복 병합
         │        → FindingVulnerability 저장
         │   ▸ 이 시점에 "무엇이 몇 건"이 확정된다
         │
         ├─ ② 탐지 0건이면 → request.complete(null) → 종료      (BR-A006)
         │
         ├─ ③ request.startExplaining(totalFindings)        → 상태 EXPLAINING
         │   findings 를 4건씩 병렬로:
         │      POST http://localhost:8000/internal/llm/explain
         │        ├─ 성공 → LlmAnalysis(SUCCESS) 저장
         │        └─ 실패 → 1회 재시도 → LlmAnalysis(FAILED) 저장, 계속 진행 (BR-L007)
         │
         ├─ ④ request.complete(overallSeverity)             → 상태 COMPLETED
         └─ Scanner 단계 예외 시 request.fail(message)       → 상태 FAILED
              │
              ▼
[React]  GET /api/v1/analyses/{id}/status  (2초 간격 폴링)
         → COMPLETED 시 결과 화면으로 이동
```

| 항목 | 값 |
| --- | --- |
| 스레드 풀 (분석 워커) | core 2 / max 4 / queue 50 |
| LLM 병렬 호출 | 분석 1건당 최대 4 동시 |
| Scanner 타임아웃 | 30초 |
| LLM 단계 전체 타임아웃 | 180초 |
| 재시도 | LLM 호출 실패 시 건별 1회 |
| 트랜잭션 경계 | 접수(동기) / 탐지 저장 / 설명 저장을 각각 분리 |
| 부분 실패 정책 | **LLM 실패는 분석 실패가 아니다.** 탐지 결과는 그대로 보존 |

> **이 구조의 장점**: 탐지가 수초 내에 끝나므로, LLM이 느리거나 실패해도
사용자는 "어디에 무슨 취약점이 있는지"를 이미 볼 수 있다.
LLM에 전부 의존할 때와 달리 **서비스가 부분적으로라도 항상 동작한다.**

### 5.3 전역 예외 처리 구조

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ApiResponse<Void>> handleBusiness(BusinessException e) {
        ErrorCode code = e.getErrorCode();
        return ResponseEntity.status(code.getHttpStatus())
                .body(ApiResponse.error(code, e.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiResponse<Void>> handleValidation(MethodArgumentNotValidException e) {
        List<FieldErrorDto> fieldErrors = e.getBindingResult().getFieldErrors().stream()
                .map(fe -> new FieldErrorDto(fe.getField(), fe.getDefaultMessage()))
                .toList();
        return ResponseEntity.badRequest()
                .body(ApiResponse.validationError(fieldErrors));
    }

    @ExceptionHandler(AccessDeniedException.class)
    public ResponseEntity<ApiResponse<Void>> handleAccessDenied(AccessDeniedException e) {
        return ResponseEntity.status(HttpStatus.FORBIDDEN)
                .body(ApiResponse.error(ErrorCode.ACCESS_DENIED));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiResponse<Void>> handleUnexpected(Exception e) {
        log.error("Unexpected error", e);   // 스택트레이스는 로그에만, 응답에는 노출 금지
        return ResponseEntity.internalServerError()
                .body(ApiResponse.error(ErrorCode.INTERNAL_SERVER_ERROR));
    }
}
```

## 8. 마무리

### 8.1 주요 포인트 요약

1. **2단계 비동기 파이프라인**: `POST /analyses` → `202` → `SCANNING`(탐지) → `EXPLAINING`(설명) → `COMPLETED`.
폴링 응답의 `stage`로 두 단계를 구분해 화면에 표시한다.
2. **탐지와 설명의 출처 분리**: 응답의 `detection` 블록은 Scanner가, `llmAnalysis` 블록은 LLM이 만든 값이다.
`ruleId`를 항상 함께 내려 어느 룰이 탐지했는지 추적할 수 있게 한다.
3. **부분 실패 허용**: LLM 호출이 실패해도 탐지 결과는 그대로 조회된다. 분석 전체가 실패하지 않는다.
4. **소유권 기반 인가**: 역할이 아닌 소유권으로 접근을 제어한다.

### 8.2 미확정 / 논의 필요 항목

| No | 논점 | 현재 설계 | 결정 필요 사항 |
| --- | --- | --- | --- |
| **D-10** | 진행 상황 전달 방식 | 2초 폴링 + `recentLogs` | 룰 기반 탐지라 로그 내용이 실제로 존재하므로 폴링으로도 화면 구현 가능. SSE는 선택 사항으로 격하 |
| **D-11** | `riskScore` 산식 | CRITICAL×20 + HIGH×10 + MEDIUM×4 + LOW×1 | 홈 화면 `위험 82` 배지 기준 확정 필요 |
| **D-12** | 분석 로그 저장 여부 | 저장하지 않음 (휘발성) | 저장한다면 `analysis_log` 테이블 추가 필요 |
| **D-13** | 즐겨찾기 / 보관됨 | API 미정의 | MVP 포함 여부 결정 (포함 시 `is_favorite`, `is_archived` 컬럼) |
| **D-14** | 보고서 PDF 지원 | markdown / json만 | PDF 필요 시 방식 결정 |
| **D-18** | `scanOptions` 저장 여부 | 요청에만 존재, 미저장 | 재분석 시 동일 옵션 재현이 필요하면 `analysis_request.scan_options JSON` 추가 |
| **D-19** | LLM 호출 단위 | 취약점 1건당 1회 | 취약점이 50건이면 호출 50회. 토큰·시간 부담이 크면 "같은 룰끼리 묶어 1회 호출"로 변경 검토 |
| **D-20** | `verdict: FALSE_POSITIVE` 처리 | 배지 표시만, 자동 제외 안 함 | 목록에서 기본 숨김 처리할지 팀 결정 필요 |
