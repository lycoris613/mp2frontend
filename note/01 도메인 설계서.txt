# 도메인 설계서

## 문서 정보

- **프로젝트명**: CodeGuard AI — 규칙 기반 보안 분석 + LLM 설명 플랫폼
- **작성자**: 홍서연
- **작성일**: 2026-09-27
- **버전**: v1.1 (Draft — 탐지 방식 확정 반영)
- **레포지토리**: https://github.com/pjt-2team-4/pjt-2team-4

> **v1.1 변경 사항**
탐지 주체를 LLM에서 **규칙 기반 Security Scanner**로 확정했다(PRD 원안 복귀).
MVP 탐지 대상은 **SQL Injection / Hardcoded Secret / XSS 3종**으로 한정하고,
LLM은 탐지된 항목의 **설명·위험성·공격 시나리오·개선 코드 생성**만 담당한다.
>

## 1. 프로젝트 개요

### 1.1 프로젝트 목적

개발자가 작성한 소스 코드를 웹에 입력하면
**규칙 기반 Scanner가 대표적인 보안 취약 패턴을 탐지**하고,
**LLM이 탐지된 취약점의 원인·위험성·공격 시나리오·개선 코드를 설명**해 주는
웹 기반 보안 코드 리뷰 서비스를 구현한다.

```
Security Scanner              LLM
"무엇이 문제인가?"     +    "왜 문제이며 어떻게 고치는가?"
(탐지·근거·위치)            (설명·위험성·개선 코드)
```

탐지를 규칙이 담당하므로 **결과 위치(파일·라인)가 항상 정확하고 재현 가능**하며,
설명을 LLM이 담당하므로 **보안 비전공자도 이해할 수 있는 리뷰**가 가능하다.
이것이 "LLM에게 전부 물어보는 서비스"와 구분되는 본 프로젝트의 구조적 차별점이다.

### 1.2 프로젝트 범위

**포함 범위 (MVP)**

- [x]  사용자 관리 (회원가입, 로그인, 로그아웃 — JWT 기반)
- [x]  코드 입력 (에디터 직접 입력 / 붙여넣기, 다중 파일)
- [x]  **규칙 기반 취약점 탐지 3종**
    - SQL Injection (CWE-89)
    - Hardcoded Secret (CWE-798)
    - XSS (CWE-79)
- [x]  탐지 항목별 LLM 분석 (설명 / 위험성 / 공격 시나리오 / 개선 방법 / 개선 코드)
- [x]  취약점 목록 조회 (유형별 / 심각도별 / 파일별 필터)
- [x]  Before / After 코드 비교 화면
- [x]  분석 결과 대시보드 (건수, 심각도 분포, 유형 분포)
- [x]  취약점 처리 상태 관리 (미해결 / 해결 / 무시)

**제외 범위 (본 MVP에서 다루지 않음)**

- [ ]  3종 외 취약점 탐지 (CORS, 민감정보 로깅, 취약한 인증 등) — Phase 2에서 룰 추가로 확장
- [ ]  AST / 데이터플로우(Taint) 기반 분석 — MVP는 정규식·패턴 기반
- [ ]  Git 저장소 연동, ZIP 업로드, 대용량 프로젝트 전체 분석
- [ ]  자동 패치 커밋 / PR 생성, CI/CD 연동, IDE 플러그인
- [ ]  팀·조직 권한 관리(RBAC)

> **왜 3종인가**: 룰 기반 탐지는 룰 1개당 "탐지 패턴 + 오탐 제외 조건 + 테스트 케이스"가 필요하다.
유형을 늘리는 것보다 3종을 **오탐 적고 설명 품질 높게** 완성하는 편이 MVP 완성도에 유리하다.
> 

### 1.3 주요 이해관계자 (Stakeholders)

| 구분 | 역할 | 주요 관심사 |
| --- | --- | --- |
| **초급 개발자 / 보안 비전공자** | 주 사용자 | 내 코드가 왜 위험한지, 어떻게 고쳐야 하는지를 쉬운 말로 알고 싶음 |
| **팀 리드 / 시니어 개발자** | 검토자 | 배포 전 위험 신호 확인, 수정 우선순위 판단 |
| **교육기관 / 스터디** | 학습 활용 | 안전한 코드 작성 학습 자료 |
| **서비스 운영자(팀)** | 시스템 운영 | 룰의 탐지율·오탐률, LLM 토큰 비용, 분석 응답시간 |

## 2. 비즈니스 도메인 분석

### 2.1 핵심 비즈니스 프로세스

#### 2.1.1 코드 보안 분석 프로세스 (핵심)

**상세 플로우**

1. **입력 단계**
    - 사용자가 로그인 후 `코드 분석` 화면 진입
    - 분석할 파일 추가 (파일명 + 상대경로 + 코드 본문)
    - 분석 제목(프로젝트명) 입력, 언어 자동 감지 확인
    - 탐지 룰 옵션 선택(예: 비밀 키 탐지 사용/미사용)
    - `취약점 분석 시작` 클릭
2. **접수 단계**
    - AnalysisRequest 생성 (상태 `PENDING`), 파일별 AnalysisFile 저장
    - 요청 즉시 `202 Accepted` + analysisId 반환
3. **탐지 단계 (Scanner, 수초 이내)**
    - 상태 `SCANNING` 전환
    - 파일별로 언어에 맞는 Scanner 실행 → 취약점 탐지
    - **탐지 결과(FindingVulnerability)를 먼저 DB에 저장** — 이 시점에 이미 "무엇이 몇 건" 확정
4. **설명 단계 (LLM, 수십 초)**
    - 상태 `EXPLAINING` 전환
    - 탐지된 취약점 **1건씩** LLM 서비스에 전달 (코드 문맥 + 룰 메타데이터)
    - 응답을 LlmAnalysis로 저장
5. **완료 단계**
    - 상태 `COMPLETED`, `completedAt` / `totalFindings` / `overallSeverity` 집계
    - Scanner 단계에서 실패하면 `FAILED`
    - **LLM 단계 일부 실패는 전체 실패로 보지 않는다** — 해당 항목만 `llm_analysis.status = FAILED`
6. **확인 단계**
    - 사용자가 취약점별 설명 / Before·After 코드 확인
    - 취약점 상태를 `RESOLVED` 또는 `IGNORED`로 변경

**비즈니스 규칙 요약**

- 1회 분석 최대 파일 수: **20개** / 파일 1개 최대 **100KB** / 총 **500KB**
- Scanner 단계 타임아웃: **30초**
- LLM 단계 전체 타임아웃: **180초**
- 분석 중(`PENDING`/`SCANNING`/`EXPLAINING`) 요청은 수정·삭제 불가

#### 2.1.2 취약점 탐지 프로세스 (Security Scanner)

> **설계 방침**: 탐지는 **정규식·패턴 기반 룰**이 담당한다.
룰은 DB가 아니라 **코드 상수로 관리**한다(버전 관리·테스트 용이, MVP에서 룰 CRUD 화면 불필요).
> 

**모듈 구조**

```
AnalysisFile (코드 본문, 언어)
        ↓
ScannerRegistry — 파일 언어에 적용 가능한 Scanner 선택
        ↓
 ┌────────────────┬────────────────────┬──────────────┐
 │ SqlInjection   │ HardcodedSecret    │ Xss          │
 │ Scanner        │ Scanner            │ Scanner      │
 └────────────────┴────────────────────┴──────────────┘
        ↓
라인 단위 매칭 → 오탐 제외 조건 적용 → 중복 병합
        ↓
FindingVulnerability (ruleId, type, cweId, severity, startLine, endLine, codeSnippet)
```

**탐지 룰 정의 (MVP 확정안)**

| 룰 ID | 유형 | 대상 언어 | 탐지 대상 | 심각도 |
| --- | --- | --- | --- | --- |
| **SQLI-001** | SQL Injection | Java | SQL 문자열에 `+` 로 변수 결합 | CRITICAL |
| **SQLI-002** | SQL Injection | Java | `Statement` + `executeQuery(변수)` 사용 | CRITICAL |
| **SQLI-003** | SQL Injection | JS/TS | 템플릿 리터럴 SQL 내 `${...}` 삽입 | CRITICAL |
| **SQLI-004** | SQL Injection | JS/TS | `db.query()` 인자에 문자열 결합 | CRITICAL |
| **SECRET-001** | Hardcoded Secret | 공통 | `password`/`pwd` 변수에 문자열 리터럴 대입 | HIGH |
| **SECRET-002** | Hardcoded Secret | 공통 | `apiKey`/`api_key`/`secret`/`token` 에 8자 이상 리터럴 대입 | HIGH |
| **SECRET-003** | Hardcoded Secret | 공통 | AWS Access Key 형식 (`AKIA[0-9A-Z]{16}`) | CRITICAL |
| **SECRET-004** | Hardcoded Secret | 공통 | Private Key 블록 (`-----BEGIN ... PRIVATE KEY-----`) | CRITICAL |
| **SECRET-005** | Hardcoded Secret | 공통 | JDBC/접속 URL 내 `password=` 평문 | HIGH |
| **XSS-001** | XSS | JS/TS | `innerHTML` / `outerHTML` 에 변수 대입 | HIGH |
| **XSS-002** | XSS | JS/TS | `document.write(변수)` | HIGH |
| **XSS-003** | XSS | JSX/TSX | `dangerouslySetInnerHTML` 사용 | MEDIUM |
| **XSS-004** | XSS | Java/JSP | `getWriter().print(request.getParameter(...))` | HIGH |
| **XSS-005** | XSS | HTML | Thymeleaf `th:utext` 사용 | MEDIUM |

> 룰 개수는 조정 가능하나, **유형은 3종을 넘기지 않는다**.
> 

**오탐(False Positive) 제외 조건**

| 조건 | 적용 룰 | 설명 |
| --- | --- | --- |
| 주석 라인 제외 | 전체 | `//`, `#`, `/* */`, `<!-- -->` 로 시작하는 라인은 스캔하지 않음 |
| 매개변수화 쿼리 인식 | SQLI-* | 같은 라인에 `?`, `$1`, `:param` 바인딩과 `PreparedStatement` 가 있으면 제외 |
| 환경변수 참조 | SECRET-* | `process.env`, `System.getenv`, `${...}`, `os.environ` 참조 시 제외 |
| 플레이스홀더 | SECRET-* | `""`, `"changeme"`, `"your-api-key"`, `"xxx"` 등 더미 값 제외 |
| 정적 문자열만 | XSS-001/002 | 대입 값이 따옴표로 시작하는 고정 문자열이면 제외 |
| 테스트 파일 | 전체 | 경로에 `/test/`, `.test.`, `.spec.` 포함 시 심각도 1단계 하향 |

**중복 병합 규칙**

- 동일 파일·동일 라인에서 서로 다른 룰이 매칭되면 **심각도가 높은 룰 1건만** 남긴다.
- 동일 룰이 연속된 라인에서 매칭되면 하나의 구간(`startLine`~`endLine`)으로 병합한다.

#### 2.1.3 LLM 분석 프로세스

> **LLM의 역할은 탐지가 아니라 설명이다.** 탐지 결과를 바꾸거나 새로운 취약점을 추가하지 않는다.
> 

```
FindingVulnerability 1건
        ↓
[Spring Boot] 프롬프트 구성
   - 룰 메타데이터 (ruleId, 유형, CWE, 심각도, 룰 설명)
   - 취약 코드 조각 + 앞뒤 문맥 (±20줄, 라인 번호 포함)
   - 파일 경로·언어
        ↓ (HTTP 내부 호출)
[FastAPI LLM Service]
   시스템 프롬프트(보안 코드 리뷰어) + JSON 출력 강제
        ↓
   { explanation, riskDescription, attackScenario,
     remediation, fixedCode, confidence, verdict }
        ↓
[Spring Boot] 스키마 검증 → LlmAnalysis 저장 (rawResponse 원문 보관)
```

**호출 전략**

| 항목 | 방침 |
| --- | --- |
| 호출 단위 | **취약점 1건당 1회** (프롬프트가 단순해져 응답 품질·파싱 안정성이 높음) |
| 동시 실행 | 최대 **4건 병렬** (스레드 풀) |
| 문맥 범위 | 취약 라인 기준 앞뒤 20줄 (파일 전체를 보내지 않아 토큰 절감) |
| 실패 처리 | 1회 재시도 → 재실패 시 해당 건만 `FAILED`, 분석 전체는 계속 진행 |
| 동일 취약점 중복 | 같은 `ruleId` + 같은 `codeSnippet` 조합은 1회만 호출하고 결과를 재사용 (토큰 절감) |

**LLM 응답의 `verdict` / `confidence` 활용**

- LLM에게 "이 룰 탐지가 실제 취약점인지" 판단하게 하고 `verdict`(`TRUE_POSITIVE` / `FALSE_POSITIVE`)와 `confidence`(0~100)를 받는다.
- **탐지 결과 자체를 삭제하지 않는다.** `FALSE_POSITIVE` 판정 시 화면에 "오탐 가능성 있음" 배지를 표시하고, 최종 판단은 사용자가 한다.
- 이 값이 와이어프레임의 `AI 신뢰도 97%` 표기에 대응한다.

#### 2.1.4 사용자 관리 프로세스

1. 이메일 + 비밀번호로 회원가입 (BCrypt 암호화 저장)
2. 로그인 시 JWT AccessToken 발급
3. 모든 분석 API는 토큰 필요, **본인이 생성한 분석만 조회 가능**

### 2.2 비즈니스 이벤트

| 이벤트 | 트리거 | 결과 |
| --- | --- | --- |
| **분석 요청 접수** | 사용자가 `분석 시작` 클릭 | AnalysisRequest(PENDING) 생성, 파일 저장, 202 응답 |
| **탐지 시작** | 비동기 워커가 요청 수신 | 상태 `SCANNING`, `startedAt` 기록 |
| **취약점 탐지 완료** | 모든 파일 스캔 종료 | Finding N건 저장, `totalFindings` 확정 |
| **설명 생성 시작** | 탐지 완료 후 | 상태 `EXPLAINING` |
| **설명 생성 완료** | 모든 Finding의 LLM 처리 종료 | LlmAnalysis N건 저장 |
| **분석 완료** | 설명 단계 종료 | 상태 `COMPLETED`, 최고 심각도 집계 |
| **분석 실패** | Scanner 오류 / 타임아웃 | 상태 `FAILED`, `errorMessage` 저장 |
| **설명 부분 실패** | 특정 Finding의 LLM 호출 실패 | 해당 `llm_analysis.status = FAILED`, 분석은 완료 처리 |
| **취약점 해결 처리** | 사용자가 `해결` 클릭 | Finding 상태 `RESOLVED` |
| **오탐 처리** | 사용자가 `무시` 클릭 | Finding 상태 `IGNORED`, 통계 제외 |

## 3. 핵심 도메인 객체 (Domain Objects)

### 3.1 도메인 객체 식별 매트릭스

| 도메인 객체 | 유형 | 중요도 | 비고 |
| --- | --- | --- | --- |
| **User (사용자)** | Entity | 높음 | 서비스 이용자, 분석 요청의 소유자 |
| **AnalysisRequest (분석 요청)** | Entity | 높음 | 분석 1회 단위 (Aggregate Root) |
| **AnalysisFile (분석 대상 파일)** | Entity | 높음 | 파일 + 코드 본문, Scanner의 입력 |
| **FindingVulnerability (탐지된 취약점)** | Entity | 높음 | Scanner가 생성하는 탐지 결과 1건 |
| **LlmAnalysis (LLM 분석 결과)** | Entity | 높음 | 취약점 1건에 대한 설명·개선안 (1:1) |
| **SecurityRule (보안 규칙)** | **Value Object (코드 상수)** | 높음 | **DB 테이블 아님** — Scanner 모듈의 룰 정의 |
| **Severity (심각도)** | Value Object (Enum) | 중간 | CRITICAL / HIGH / MEDIUM / LOW |
| **AnalysisStatus (분석 상태)** | Value Object (Enum) | 중간 | PENDING / SCANNING / EXPLAINING / COMPLETED / FAILED |
| **FindingStatus (처리 상태)** | Value Object (Enum) | 중간 | OPEN / RESOLVED / IGNORED |
| **VulnerabilityType (취약점 유형)** | Value Object (Enum) | 중간 | **SQL_INJECTION / HARDCODED_SECRET / XSS** 3종 |

### 3.2 상세 도메인 객체 정의

#### 3.2.1 User (사용자)

**역할**: CodeGuard AI 서비스를 이용하는 개발자

**주요 속성**: `id`, `email`(유일, 로그인 ID), `password`(BCrypt), `createdAt`, `updatedAt`

**주요 행동**: `changePassword(encoded)`, `owns(analysisRequest)`

**비즈니스 규칙**

- 이메일은 유일하며 로그인 ID로 사용한다
- 비밀번호는 평문 저장 금지, 응답 DTO에 포함하지 않는다
- 본인이 생성한 분석만 조회·삭제할 수 있다

#### 3.2.2 AnalysisRequest (분석 요청)

**역할**: 사용자가 한 번 요청한 분석 작업 전체를 나타내는 Aggregate Root

**주요 속성**

- `id`, `user`(FK), `title`(화면상 프로젝트명)
- `status`: PENDING / SCANNING / EXPLAINING / COMPLETED / FAILED
- `overallSeverity`, `totalFiles`, `totalFindings`
- `errorMessage`, `startedAt`, `completedAt`

**주요 행동**

- `startScanning()` : PENDING → SCANNING
- `startExplaining(totalFindings)` : SCANNING → EXPLAINING
- `complete(overallSeverity)` : EXPLAINING → COMPLETED
- `fail(message)` : 진행 중 → FAILED
- `isInProgress()`, `getDurationSeconds()`, `getResolutionRate()`

**비즈니스 규칙**

- 상태 전이는 `PENDING → SCANNING → EXPLAINING → COMPLETED | FAILED` 순서만 허용
- 탐지 결과가 0건이면 EXPLAINING을 건너뛰고 바로 COMPLETED로 전이한다
- 진행 중인 요청은 삭제할 수 없다
- 삭제 시 하위 파일·취약점·LLM 결과가 함께 삭제된다

#### 3.2.3 AnalysisFile (분석 대상 파일)

**역할**: 분석 요청에 포함된 개별 소스 파일과 코드 본문. **Scanner의 입력 단위**

**주요 속성**

- `id`, `analysisRequest`(FK), `relativePath`, `fileName`, `extension`, `language`
- `content`: 코드 본문 *(※ ver2 ERD 누락 — 추가 필수)*
- `fileSizeBytes`

**주요 행동**

- `getLines()`: 라인 배열 반환 (Scanner가 라인 단위로 순회)
- `extractSnippet(start, end)`: 구간 추출 (Before 표시용)
- `extractContext(line, padding)`: 문맥 추출 (LLM 프롬프트용, 기본 ±20줄)
- `detectLanguage()`: 확장자 기반 언어 판별

**비즈니스 규칙**

- 동일 분석 내 `relativePath` 중복 불가
- 파일 1개는 100KB 초과 불가
- 지원하지 않는 확장자는 분석 대상에서 제외한다
- **지원 언어가 아니면 Scanner를 실행하지 않는다** (탐지 0건으로 처리)

#### 3.2.4 FindingVulnerability (탐지된 취약점)

**역할**: **Scanner가 탐지한** 취약점 1건. 파일의 특정 라인 구간에 대응한다.

**주요 속성**

- `id`, `analysisFile`(FK)
- `ruleId`: 탐지한 룰 식별자 (예: `SQLI-003`) *(※ ver2 ERD 누락 — 추가 권장)*
- `vulnerabilityType`: SQL_INJECTION / HARDCODED_SECRET / XSS
- `cweId`: CWE 식별자 (룰이 부여) *(※ ver2 ERD 누락 — 추가 권장)*
- `severity`: **룰이 정의한 심각도** (LLM이 정하지 않는다)
- `status`: OPEN / RESOLVED / IGNORED
- `startLine`, `endLine`, `codeSnippet`

**주요 행동**

- `resolve()`, `ignore()`, `reopen()`
- `isCritical()`, `getLineRange()`
- `mergeWith(other)`: 연속 라인 매칭 병합

**비즈니스 규칙**

- **생성 주체는 Scanner이며 LLM은 생성·삭제·수정할 수 없다**
- `startLine <= endLine`, 파일 라인 수를 초과할 수 없다
- 심각도는 룰 정의값을 따르되 테스트 파일은 1단계 하향한다
- `IGNORED` 항목은 대시보드 집계에서 제외한다
- 취약점은 반드시 하나의 LlmAnalysis를 가진다 (생성 실패 시 status=FAILED 레코드)

#### 3.2.5 LlmAnalysis (LLM 분석 결과)

**역할**: 탐지된 취약점 1건에 대한 LLM의 설명과 개선 제안

**주요 속성**

- `id`, `finding`(FK, **UNIQUE**)
- `status`: PENDING / SUCCESS / FAILED
- `explanation`, `riskDescription`, `attackScenario`, `remediation`, `fixedCode`
- `verdict`: TRUE_POSITIVE / FALSE_POSITIVE / UNCERTAIN *(신규 제안)*
- `confidence`: 0~100 *(신규 제안 — 화면의 `AI 신뢰도`)*
- `modelName`, `promptVersion`, `rawResponse`
- `promptTokens`, `completionTokens`, `errorMessage`

**주요 행동**: `getTotalTokens()`, `hasFixedCode()`, `isSuccess()`, `isLikelyFalsePositive()`

**비즈니스 규칙**

- 하나의 Finding 당 LlmAnalysis는 1건만 존재한다 (UNIQUE)
- `rawResponse`는 파싱 성공 여부와 무관하게 저장한다
- 프롬프트 변경 시 `promptVersion`을 반드시 갱신한다
- **LLM 판정은 참고값이며 탐지 결과를 자동으로 제거하지 않는다**
- 토큰 사용량은 운영 비용 산정 근거로 누적 집계한다

#### 3.2.6 SecurityRule (보안 규칙) — Value Object

**역할**: Scanner가 사용하는 탐지 규칙 1개의 정의. **DB 테이블이 아니라 코드 상수**다.

**주요 속성**

- `ruleId`: 룰 식별자 (`SQLI-003`)
- `vulnerabilityType`, `cweId`, `severity`
- `targetLanguages`: 적용 언어 집합
- `pattern`: 탐지 정규식
- `excludePatterns`: 오탐 제외 정규식 목록
- `title`, `description`: 룰 설명 (LLM 프롬프트에 함께 전달)

**주요 행동**

- `matches(line)`: 라인 매칭 여부
- `isExcluded(line)`: 오탐 제외 조건 해당 여부
- `appliesTo(language)`: 해당 언어에 적용 가능한지

**비즈니스 규칙**

- 룰은 **불변(immutable)** 이며 런타임에 변경되지 않는다
- 룰 추가·수정 시 반드시 단위 테스트(취약 코드 / 안전 코드 쌍)를 함께 추가한다
- `ruleId`는 전역 유일하며 이력 추적을 위해 재사용하지 않는다

## 4. 도메인 관계도

### 4.1 개념적 관계도

```
[User]                 1 ──── N [AnalysisRequest]
[AnalysisRequest]      1 ──── N [AnalysisFile]
[AnalysisFile]         1 ──── N [FindingVulnerability]
[FindingVulnerability] 1 ──── 1 [LlmAnalysis]

[SecurityRule] ┄┄(참조)┄┄▶ [FindingVulnerability.ruleId]
   ※ 코드 상수이므로 DB 관계가 아니라 식별자 참조
```

```
User
 └─ AnalysisRequest (분석 1회)
      └─ AnalysisFile (파일 N개, 코드 본문 포함)   ← Scanner 입력
           └─ FindingVulnerability (취약점 N건)    ← Scanner 출력
                └─ LlmAnalysis (설명·개선코드 1건) ← LLM 출력
```

### 4.2 관계 상세 설명

| 관계 | 카디널리티 | 설명 | 제약조건 |
| --- | --- | --- | --- |
| **User ↔ AnalysisRequest** | 1:N | 한 사용자는 여러 분석 요청 | 소유자 본인만 조회 |
| **AnalysisRequest ↔ AnalysisFile** | 1:N | 한 분석은 여러 파일 포함 | 1~20개, 경로 중복 불가, Cascade |
| **AnalysisFile ↔ FindingVulnerability** | 1:N | 한 파일에서 여러 취약점 탐지 | 0건 가능, Cascade |
| **FindingVulnerability ↔ LlmAnalysis** | 1:1 | 취약점 1건당 설명 1건 | finding_id UNIQUE, Cascade |

> **파일 단위 FK가 타당한 이유**: Scanner는 파일 단위로 동작하고 결과도 파일의 라인에 귀속된다.
ver1처럼 Finding이 `analysis_request_id`를 직접 참조하면 "어느 파일의 몇 번째 줄인지"를 별도 컬럼으로 또 관리해야 한다.
**ver2의 `analysis_file_id` FK 구조가 규칙 기반 탐지에 더 적합하다.**
> 

### 4.3 Aggregate 경계

| Aggregate Root | 포함 Entity | 경계 설정 이유 |
| --- | --- | --- |
| **User** | User | 인증·인가 단위 |
| **AnalysisRequest** | AnalysisRequest, AnalysisFile, FindingVulnerability, LlmAnalysis | 분석 1회가 트랜잭션·삭제·조회 단위 |

> Scanner와 LLM 모듈은 **도메인 서비스**로서 Aggregate 외부에 위치하며,
결과를 Root를 통해서만 반영한다 (`analysisFile.addFinding(...)`, `finding.attachLlmAnalysis(...)`).
>

## 6. 용어 정의 (Glossary)

### 6.1 비즈니스 용어

| 용어 | 정의 | 영문 | 비고 |
| --- | --- | --- | --- |
| **분석 요청** | 사용자가 한 번에 요청한 분석 작업 단위 | Analysis Request | 화면상 "프로젝트"로 표시 |
| **탐지 룰** | Scanner가 사용하는 패턴 정의 1개 | Security Rule | 코드 상수, 예: `SQLI-003` |
| **탐지된 취약점** | 룰에 매칭되어 생성된 결과 1건 | Finding | 파일·라인에 귀속 |
| **오탐 제외 조건** | 룰 매칭을 무효화하는 조건 | Exclusion Rule | 주석·환경변수·바인딩 등 |
| **심각도** | 룰이 정의한 위험 정도 | Severity | 치명적/높음/중간/낮음 |
| **AI 신뢰도** | LLM이 판단한 실제 취약점일 확신도 | Confidence | 참고값, 탐지를 무효화하지 않음 |
| **오탐** | 실제로는 취약하지 않은데 탐지된 경우 | False Positive | 사용자가 IGNORED 처리 |
| **해결률** | 전체 취약점 중 RESOLVED 비율 | Resolution Rate | IGNORED 제외 |
| **Before / After** | 취약 코드와 LLM 제안 개선 코드의 비교 | — | 결과 화면 하단 |
| **프롬프트 버전** | LLM에 전달한 프롬프트의 관리 버전 | Prompt Version | 품질 추적 기준 |

### 6.2 보안 용어

| 용어 | 정의 | 영문 | CWE |
| --- | --- | --- | --- |
| **SQL 삽입** | 사용자 입력이 SQL 문에 직접 결합되어 쿼리가 조작되는 취약점 | SQL Injection | CWE-89 |
| **하드코딩된 비밀정보** | API 키·비밀번호를 소스 코드에 직접 기입 | Hardcoded Secret | CWE-798 |
| **XSS** | 검증되지 않은 입력이 페이지에 출력되어 스크립트가 실행되는 취약점 | Cross-Site Scripting | CWE-79 |
| **매개변수화 쿼리** | SQL 문과 입력값을 분리해 바인딩하는 방식 | Prepared Statement | SQLI 대응 |
| **정적 분석** | 실행하지 않고 소스 코드를 분석하는 기법 | SAST | 본 프로젝트의 Scanner |
| **CWE** | 공통 취약점 유형 분류 체계 | Common Weakness Enumeration | — |
